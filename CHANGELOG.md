# Changelog

## Unreleased

- **Tests: chaos scenario 07 (half-open) now really exercises "200, then close" and fails if it does not (qfg-6vno.4 follow-up).** The rig sized toxiproxy's `limit_data` from a response head measured with a `Connection: close` request (433 bytes), but the SDK's keep-alive request gets a 438-byte head, so every attempt in the window was cut inside its headers and failed as a transport error. 07 still passed on those errors. The head is now measured with the SDK's own request headers, and the rig checks, when the inject is cleared, that at least one attempt got a 200 and then EOF before its first frame (a new internal test-only SSE counter). No public API or runtime behavior change.
- **Fixed (minor): on .NET Framework hosts (the netstandard2.0 build), closing the client or entering auth-failed no longer waits 5 s for the SSE stream (qfg-6vno.13).** On netstandard2.0 the SSE read could not be cancelled, so cancelling it left a connected read blocked. `CloseAsync()` waited its full 5 s before disposing, and the auth-failed entry waited 5 s and then could leave a live stream open until the 90 s read watchdog fired. Cancelling the SSE token now disposes the response body, which unblocks the read at once, the same way the watchdog does. The net8.0 build already cancelled the read; it gets the same safeguard.
- **Fixed (patch): `OnConfigChange` handlers no longer run while the SDK holds its install lock (qfg-6vno.12).** Before, every network install (initial fetch, refresh / fallback poll, SSE update) fired `OnConfigChange` inside the lock that serializes installs. A slow handler stalled the SSE reader, the fallback poller and every refresh, and a handler that waited on another thread doing an install deadlocked. Handlers now run after the lock is released. They are still serialized and in install order: a change installed while a handler is running is delivered after that handler returns, possibly on the thread that is already delivering. The initial-load handler still fires before `InitAsync()` returns. Getters were never affected. Same fix as sdk-go qfg-eefx.

## 1.9.0 - 2026-10-21

- **Changed (minor): init failure uses `OnInitFailure.Fail` / `Wait` / `Continue`, retries until `InitTimeout`, and adds a readiness API (qfg-9p4i.10).** **UPGRADE: when delivery is unreachable, `InitAsync()` now retries until `InitTimeout` (10 s by default) before it fails or continues, and throws `QuonfigInitException`; rename `OnInitFailure.Throw` to `Fail` and `ReturnDefaults` to `Continue`.** Spec: `project/plans/2026-10-05-init-failure-design.md`, sections B and C.
  - **Retry before the timeout.** Each attempt is one hedged primary+secondary fetch, with jittered backoff between attempts (0.5 s, 1 s, 2 s, ... capped at 30 s). Before, the first failed attempt decided at once, so a refused connection or a 5xx failed (`Throw`) or continued (`ReturnDefaults`) within milliseconds. A boot during an outage now takes up to `InitTimeout`. A healthy boot is unchanged.
  - **`Fail` (the default, same value as `Throw`).** At the timeout `InitAsync()` throws `QuonfigInitTimeoutException` if no leg answered, or `QuonfigInitException` with `Reason = Unavailable` if the legs answered with errors (before, a bare `QuonfigException`). If every configured leg answers 401, 403, 404 or 410 it throws at once with `Reason = Unauthorized`. `QuonfigInitException` derives from `QuonfigException`, and `QuonfigInitTimeoutException` now derives from `QuonfigInitException`, so existing `catch` blocks still match. A client you keep after catching the exception keeps retrying and heals.
  - **`Continue` (same value as `ReturnDefaults`).** At the timeout `InitAsync()` returns and getters serve code defaults until the background retry heals. A 401/403/404/410 from every configured leg continues at once.
  - **`Wait` (new).** `InitAsync()` keeps blocking past the timeout, with no upper bound, until the first config arrives or your `CancellationToken` fires. A 401/403/404/410 from every leg is logged at `Error` and retried, since the key may be provisioned late. Under ASP.NET Core this holds host start until config lands.
  - **Deprecated aliases.** `OnInitFailure.Throw` and `ReturnDefaults` are `[Obsolete]` and keep their values, so code that uses them behaves exactly like `Fail` / `Continue`. They raise compiler warning CS0618 at the call site; a project built with `TreatWarningsAsErrors` must rename them. Because the alias and the new name are the same value, there is no runtime deprecation log line.
  - **Readiness API (new).** `Quonfig.IsReady` is true once the client holds a config from Quonfig, and `Quonfig.WaitForReadyAsync(CancellationToken)` completes when it does, in every mode. Under `Wait`, wire your readiness probe to `IsReady`. They are on the `Quonfig` class only, not on `IQuonfig`, so hand-written `IQuonfig` implementations keep compiling.
  - **The `InitTimeout` deadline is measured from construction**, not from the `InitAsync()` call. Code that awaits `InitAsync()` right after construction sees no difference.
  - **Init log lines follow the cross-SDK contract.** They start with `[quonfig]`, carry an `EventId` named `quonfig.init.<event>`, name the failing hosts (never the SDK key), and come at these levels: `Debug` at start; `Warning` on the first failed attempt and every 5 s until the timeout; `Error` at a `Fail` or `Continue` timeout and on a rejected key; `Warning` at a `Wait` timeout and every 30 s after; `Warning` every 30 s for 5 minutes (then every 5 minutes) while a kept client is still not ready; and one `Warning` when it recovers. They replace the `quonfig: initial config fetch failed under OnInitFailure...` warnings. A healthy boot logs nothing above `Debug` from init.
- **Init-failure conformance fixes (qfg-9p4i.17.5), part of the same minor.**
  - **Unauthorized fast-fail uses the full auth class and every configured leg.** `Fail` throws `Reason = Unauthorized` (and `Continue` continues) at once only when every configured delivery URL answers 401, 403, 404 or 410 (was 401/403). With three or more `ApiUrls` the init path now asks the legs the hedge does not fire before deciding, so the rule is reachable (and a healthy third leg is installed).
  - **`InitTimeout` <= 0 means one attempt, then `OnInitFailure`.** Before, zero or a negative value threw inside the HTTP transport and left the client permanently dead in every mode, and `Timeout.InfiniteTimeSpan` decided before any attempt. `InitTimeout` also no longer becomes the shared `HttpClient.Timeout`, so a small value no longer caps every later fetch (wait-mode retries, the fallback poller, `RefreshAsync`).
  - **Timeout vs unavailable follows the last attempt.** `QuonfigInitTimeoutException` only when every leg of the last attempt timed out (or no attempt completed); a fast error on any leg makes it `Unavailable`. Its message now names the failing hosts like the `Unavailable` variant (was `...exceeded 00:00:10`).
  - **No URL credentials in errors.** Transport error messages (and so init log lines and the init exception's inner exceptions) print the URL without `user:pass@` userinfo.
- **Tests: the Test and Release workflows pin integration-test-data `v2026.10.21.1` (was `v2026.10.16.4`).** It adds the init-failure cases: fail by default, `fail` with refused, hung and 401 legs, `continue`, the `raise` / `return` aliases, per-leg 404/410 and mixed-status classification, `init_timeout_ms` 0, and no-userinfo messages. The refused-leg cases run one attempt, so the full suite runs on the Windows runners with no filter. The chaos workflow pins are unchanged.
- **Fixed (patch): a client that survives a caught `OnInitFailure.Throw` now keeps retrying and heals (qfg-9p4i.3).** When the initial config fetch failed under `Throw` (the default), `InitAsync()` raised and the client never started its update channel, so a caller that caught the exception and kept the object served code defaults forever. Only `ReturnDefaults` started SSE and the fallback poller. Now `Throw` starts them too: `InitAsync()` still raises exactly as before, and the kept client installs the first envelope once delivery is reachable, then stays live. A Warning is logged when the background retry starts. Discarding the client after the exception, as before, is unaffected.

## 1.8.0 - 2026-10-20

- **Changed (minor): SSE counts as connected at the first frame, not at the 200 response (qfg-goi1.10.41).** **UPGRADE: SSE reports `connected` at the first frame, not at the 200 response (qfg-goi1.10.9).** A stream connection now counts as connected, for `ConnectionState`, the `OnConnectionStateChange` event, the reconnect backoff and the fallback poller, only after it delivers its first valid frame: a config envelope or a keepalive. Before, it counted as soon as the 200 response headers arrived.
  - Against Quonfig's servers the headers and the first frame arrive together, so you should see no difference.
  - Behind a proxy or server that sends 200 headers early, `connected` is reported when the first frame arrives: at most one keepalive interval (30 s) later.
  - A connection that closes before any frame is now a failed attempt. The reconnect delay grows, the client reports disconnected, and the fallback poller takes over after its usual threshold.

  Before this change, a server that answered 200 and closed at once made the SDK reconnect in a tight loop and keep stale config indefinitely. In sdk-net the reconnect delay already grew for a 200 with an empty body, but every attempt still reported `Connected` and cancelled the fallback poller's 120 s timer, so the poller never took over; and one stray or partial line (a garbage `data:` block, a keepalive cut off by the close) reset the delay to 1 s. A frame is a blank-line-terminated block that is comment-only or whose `data:` decodes as a config envelope; headers alone, a block cut off by EOF, malformed or non-envelope data, and an `id:`-only block are not. The public `SseClient.ParseStreamAsync` keeps its signature; its `bool` result now means "a valid frame was seen" instead of "any line was read". Keepalives still do not advance `LastSuccessfulRefresh`. The fallback poller also restarts its 120 s threshold from the latest disconnect when a connection delivers a frame and closes at once. Before, its worker could miss that brief connected edge and engage at the earlier disconnect's deadline. Pinned by supervisor contract Test 9 and the Test 2 reset rule (integration-test-data `v2026.10.16.4`), same rule as sdk-go.
- **Fixed (patch): the SSE reconnect backoff caps at 30 s, jitter included (qfg-n3nr).** It capped at 60 s with +/-20% jitter, so after a long stream outage the next reconnect could land up to 72 s after the server came back (the fallback poller kept config fresh meanwhile). It now caps at 30 s like sdk-go, sdk-node, sdk-python and supervisor contract Test 2, and the jitter never pushes a sleep past the cap. `SseClient.DefaultMaxBackoff` is now 30 s; a `maxBackoff` passed to the `SseClient` constructor is still honored.
- **Fixed (patch): `ConnectionState` no longer reads `Connected` right after `InitAsync()` before any stream exists.** In HTTP mode with a stream configured, `InitAsync()` completes when the init fetch installs, just before the SSE worker starts. In that window `ConnectionState` read `Connected`, then went back to `Initializing` once the worker existed, and `Connected` again at the first frame. It now reads `Initializing` until the stream delivers its first frame, like sdk-go and sdk-java. Datadir and datafile modes still read `Connected` once the config is installed, and so does HTTP mode without stream URLs.
- **Tests: the Test and Release workflows pin integration-test-data `v2026.10.16.4` (was `v2026.10.16.1`).** The regenerated `get_or_raise` init-timeout cases now point at `http://192.0.2.1:1` (TEST-NET-1) instead of a staging host; both pass. The chaos workflow pins are unchanged.

## 1.7.0 - 2026-10-16

- **Changed (minor): a rejected SDK key slows down instead of polling at the normal cadence (auth-failure rule, qfg-goi1.10.28).** **UPGRADE: retry cadence and log levels change after a rejected 401/403/404/410 fetch cycle; a revoked key logs one config ERROR.** When a fallback-poller cycle gets no 200/304 on any leg and the primary leg answered 401, 403, 404 or 410, the client enters an internal auth-failed regime: SSE is stopped, the fallback poller stops, and the client sends one fetch probe across every leg every 150-300 s (uniform, re-drawn each time, no doubling, never giving up). Before, the poller kept fetching every 60 s in `FallingBack` forever and every rejected cycle was silent. The client logs one `Error` naming the status and host (never the key) on entry, `Debug` per probe, and one `Information` on exit. The first probe that gets a valid 200 or a 304 on any leg installs it, leaves auth-failed and restarts SSE as a new stream from its base backoff; the poller is back on its 120 s engage rule. `ConnectionState` is `Disconnected` while auth-failed (never `FallingBack`); there is no new state or getter. A primary 503 with a secondary 401, a 200 or 304 on any leg, or an SSE 401 on its own never enters; SSE behavior and its log lines before entry are unchanged. sdk-net has no polling mode (without stream URLs there is no background refresh), so only the fallback poller can enter. Pinned by supervisor Test 8 (integration-test-data v2026.10.16), same rule as sdk-go.
- **Changed (minor): rule operators follow the canonical cross-SDK semantics pinned in integration-test-data `v2026.10.16.1` (qfg-goi1.5.5).** **UPGRADE: pass dates as epoch milliseconds (a number or an all-digit string) or ISO 8601 / RFC3339 with `Z` or a numeric offset, such as `2025-01-01T00:00:00Z` or `2025-01-01T09:00:00+09:00`.** Three rules change who matches:
  - **`PROP_IS_ONE_OF` and the other string operators on a `bool` context value.** A `bool` now reads `"true"` / `"false"`, so "is one of `true`" matches a context `beta = true` (it never matched before, because .NET stringified it as `"True"`). A `["True"]` / `["False"]` list written as a workaround stops matching; change it to lowercase. A whole-number `double`, `float` or `decimal` reads as plain digits (`1.0` -> `"1"`, `1e15` -> `"1000000000000000"`, `1234567.0m` -> `"1234567"`) on every runtime; before, `decimal` kept its scale and .NET Framework printed `1E+15`.
  - **`PROP_SEMVER_*` accepts abbreviated versions.** `"2"` and `"2.0"` read as `2.0.0` on both the context and the rule side, so a context `version = "4.1"` now matches "greater than `4.0.18`" (before, an abbreviated version never matched). A `v` prefix is still invalid. The public `SemanticVersion.TryParse` / `Parse` stay strict SemVer 2.0.
  - **`PROP_BEFORE` / `PROP_AFTER` parse one strict grammar, on both the context value and the rule value.** Accepted: a number (epoch ms), an all-digit string (epoch ms), or RFC3339 with `Z` or an offset (fractional seconds allowed). Date-only (`"2024-11-01"`), offset-less (`"2024-11-01T00:00:00"`) and free-form (`"Nov 1 2024"`) strings no longer parse, so the criterion does not match; before, `DateTimeOffset.TryParse` accepted them and read them as UTC. Rules written by the Quonfig UI or `qfg` already store epoch ms, and `qfg verify` rejects the other forms.
  - Approved as a minor under Decision 1 (qfg-goi1.5).
- **Docs: the README says that the SDK adds the `qfg login` email as `quonfig-user.email` to every evaluation by default, and how to turn that off (qfg-goi1.2.41).** No code change.
- **Fixed (patch): an SSE connect to a peer that accepts the connection but never sends response headers no longer wedges streaming forever (qfg-goi1.2.37).** The read watchdog only arms once headers arrive, and the stream request has no `HttpClient.Timeout`, so such a peer (a hung proxy or load balancer) left the client waiting on one connect attempt indefinitely and never reconnected. Each connect now waits at most 90 s for headers, then logs a `Warning` and reconnects with the usual backoff. The 90 s bound is fixed and separate from `SseReadTimeout` on purpose: api-delivery sends headers with the first event, which on a cold workspace is the 30 s heartbeat, so a header wait tied to a short read timeout would reconnect forever (as sdk-go and sdk-java found under the chaos latency scenario). Same fix as sdk-go and sdk-java.

## 1.6.0 - 2026-10-09

- **Fixed: evaluation-summary telemetry grew one counter per evaluation for a `json` config whose value comes from an `ENV_VAR` (qfg-goi1.2.2).** The SDK re-parses that value into a new dictionary on every evaluation, and counters were grouped by object reference, so a window of 200k `GetJson` calls kept about 135 MB and sent a 26 MB telemetry POST. Counters now group JSON objects, arrays and string lists by their canonical JSON text (object keys sorted), so equal values share one counter. `TelemetryMaxEvaluationSummaries` (10,000) now caps the distinct counters per window, as in sdk-go, instead of only the distinct config keys; a new counter past the cap is not recorded, and counters already recorded keep counting.
- **Fixed: a `decryptWith` key config is now evaluated in the client's environment, so an environment-scoped key rule applies (qfg-goi1.2.14).** The key config was evaluated with no environment, so only its default rules applied. In a workspace whose key config has a default rule plus an environment rule (for example a default `QUONFIG_ENCRYPTION_KEY` rule and a `production` `QUONFIG_ENCRYPTION_KEY_PROD` rule), every secret in that environment was decrypted with the default key and failed (`QuonfigDecryptionException`, or `Reason.Error` from `Get*Details`), while `GetString` on the key config itself returned the environment's key. This matches sdk-go, sdk-node, sdk-java and sdk-ruby. **Edge that changes:** a secret encrypted with the *default* key, read in an environment whose key rule points at a different key, decrypted before and now fails, as it already does in those SDKs; re-encrypt it with that environment's key. The public `Resolver.KeyResolver` delegate and `Resolver.Resolve` overloads are unchanged.
- **Fixed: the fallback poller no longer wakes every 5 ms while idle (qfg-goi1.2.15).** With SSE connected (the normal state, and the poller is on by default) its worker waited for an SSE state change by looping a 5 ms `Task.Delay`, about 200 timer wakeups per second for the life of every client (measured at about 11% of a CPU core per idle client). It now parks on a signal that `SetSseConnected` completes, plus one deadline timer, so an idle client wakes only on an SSE state change, its threshold or interval deadline, or shutdown. State edges are still delivered immediately, including one that lands while the worker runs its callbacks or fetch (qfg-vov2).
- **Fixed: `GetJson` and `GetStringList` (and their `Details` variants) return a copy of the stored value, so editing a result no longer changes the config for every other caller (qfg-goi1.2.15).** They returned the client's cached object, so code that added a field to a returned dictionary before serializing it, or edited a returned list, silently changed what later evaluations returned until the next config update. The copy is deep and keeps the runtime types (`Dictionary<string, object?>`, `List<object?>`, `List<string>`, `string[]`), so code that casts the result keeps working. A `defaultValue` you pass is still returned as is. Each call now allocates its own copy, so two calls return different objects (compare by value, not by reference); code that reads a large JSON config in a hot loop should read it once and reuse the result.
- **Fixed: a telemetry failure while recording an evaluation can no longer escape a getter (qfg-goi1.2.15).** For example, a caller editing a `GetJson` result while another thread evaluated the same config could throw `InvalidOperationException` out of `GetJsonDetails`, breaking the 1.5.0 "`Get*Details` never throw" contract. The evaluation result is returned as normal, the client logs one `Warning` for the first such failure, and a JSON value whose canonical text cannot be computed is counted by reference instead of being dropped.
- **Fixed: a `PROP_MATCHES` / `PROP_DOES_NOT_MATCH` rule can no longer pin the calling thread on a catastrophic-backtracking regex (qfg-goi1.2.15).** The regex ran with no time limit on the caller's thread, so a pattern such as `^(a+)+$` against a 29-character input took about 16 s inside one `IsFeatureEnabled` call. Each match now has a 100 ms timeout; a timeout fails closed (the criterion does not match, for both operators), as an invalid pattern already did, and the client logs one `Warning` per config key naming the config and the property (never the context value). A match that finishes within 100 ms is unaffected. A costly pattern on a long input, or a match delayed by a starved thread pool or a GC pause, can hit the limit; that evaluation then does not match, and the warning makes it visible.
- **Fixed: an example context sent in telemetry is the context as it was at evaluation time (qfg-goi1.2.15).** The collector kept a reference to the caller's `ContextSet` (the caller's own object when no `GlobalContext` is set) and read it up to 60 s later at upload, so edits made after the evaluation were sent instead, and an edit during the upload could fail that telemetry window. The context is now copied when an example is kept, after the once-per-hour-per-key rate limit, so the cost is per example, not per evaluation.
- **Fixed: an `ENV_VAR` value that cannot be converted to the config's type no longer appears in the exception message or `ErrorMessage` (qfg-goi1.2.15).** The `QuonfigCoercionException` message (thrown by the plain getters under `OnNoDefault.Throw`, and returned as `ErrorMessage` by `Get*Details`) quoted the raw value twice, once directly and once inside the parser's own message, even for a `confidential` config, and callers and the OpenFeature provider log those messages. It now reads `environment variable "<NAME>" cannot be converted to <type> for config "<key>"`, where `<type>` is the config-file type name (`int`, `string_list`, ...). This is the wording of sdk-go's matching fix (qfg-goi1.2.4, not yet released); sdk-go also appends a sanitized parser reason, which .NET parser messages cannot give without the value, so the parser exception is attached as `InnerException` instead. Message text only; the exception type and `ErrorCode` are unchanged.
- **Fixed: the SSE reconnect after a stream that delivered data is jittered (qfg-goi1.2.15).** It always slept exactly the initial backoff (1 s), so when an api-delivery deploy closed every stream, all clients reconnected in lockstep. That sleep now gets the same +/-20% jitter as the failure backoff, as in sdk-go.
- **Tests: the chaos harness reports `server_metric(...)` expectations as SKIPPED with a reason instead of passing them against a stubbed 0 (qfg-goi1.1.5).** api-delivery exports metrics via OTLP push only and the rig has no scrape endpoint, so `server_metric('quonfig_subscriber_lag_seconds') == 0` used to pass without checking anything. The expression evaluator is now pass / fail / skipped: a skipped leaf is neutral inside AND/OR, so scenario 02 still enforces `connectionState() == 'connected'`. Each skipped expectation prints a `SKIP` line with the reason, and `scripts/run-chaos.sh` ends with a "chaos skipped expressions" tally (also written to the GitHub job summary). Server lag stays covered by the staging drill qfg-47c2.19 and the `QuonfigSubscriberLagHigh` alert. CI/test only; no release needed.
- **Tests: the chaos harness fails an expectation on an `sdkMetric` name the probe does not implement, instead of comparing it against 0 (qfg-goi1.2.23).** `client.sdkMetric('typo_total') == 0` used to pass without checking anything. The probe now reports whether it knows the metric, as sdk-go's does, and the expectation fails with `unknown sdkMetric "<name>": the chaos probe does not implement it`. The probe implements only `quonfig_sdk_worker_restart_total`, so the `quonfig_sse_connect_attempts_total < 100` expectation in scenario 09 (flapping), which passed vacuously, now fails until the probe counts connect attempts. CI/test only; no release needed.
- **Tests: the chaos probe counts `quonfig_sse_connect_attempts_total` (qfg-goi1.2.43).** It adds one for every transition into connected, as sdk-go's probe does. Scenario 09 (flapping) asserts this metric stays below 100 for 30 s; since qfg-goi1.2.23 that expectation failed with `unknown sdkMetric "quonfig_sse_connect_attempts_total"`, which turned the Chaos check red on every push and PR. It is now checked against a real count. CI/test only; no release needed.
- **CI: the chaos and failover-chaos workflows pin integration-test-data `v2026.10.03`, the same tag as the unit tests (qfg-goi1.1.5).** They pinned `v2026.05.13` and `v2026.06.19.1`. The only scenario change in that range is the 60-second freshness hold in `05-sse-down` (qfg-e3ja). api-delivery stays on `main` on purpose (the chaos runs exist to catch its drift); both workflows now write the resolved api-delivery SHA and the ITD tag to the job summary. CI only.
- **CI: the Test workflow regenerates the integration-test-data tests at the pinned tag and fails if they differ from the committed copy (qfg-goi1.1.5).** Before, a tag bump without regenerating kept running the old generated tests. CI only.

## 1.5.0 - 2026-10-02

- **Fixed: the evaluation-summary telemetry marker of an encrypted (`decryptWith`) value is now hashed from the stored ciphertext, not the decrypted plaintext (qfg-2agi.34).** This matches the cross-SDK contract and the integration-test-data case `confidential encrypted string is redacted using ciphertext hash` (`*****936c9`, before: `*****18aa7`). The plaintext was never sent; only the 5-character hash prefix changes.
- **Tests: the integration-test-data suite now runs every case through the public client (qfg-2agi.34).** The generated tests call the typed getter named by each case's `type` (`GetString`, `GetLong`, `GetDouble`, `GetBool`, `GetStringList`, `GetJson`, `GetDuration`) or `IsFeatureEnabled`; they pass the global, block and local context tiers through `GlobalContext`, `WithContext` and the per-call contexts argument instead of merging them in the test; telemetry cases evaluate through a client with a capturing `ITelemetrySender` and assert what the real reporter sends. Raise cases assert the exact exception type, including `QuonfigCoercionException`; the harness no longer throws exceptions itself or maps one exception type to another, and its copy of the resolver, the telemetry value hashing and the weighted-bucket selection is removed. A planted bug in each of these now fails the suite: `GetDuration`, `IsFeatureEnabled`, a typed getter's default, `GlobalContext`, the telemetry reason, telemetry redaction, and raising under `OnNoDefault.Throw`. The rewrite exposed one existing bug, fixed above (telemetry marker of an encrypted value). No behavior change.
- **Fixed: duration values are parsed by one strict ISO-8601 parser that implements the shared Quonfig grammar, for stored and `ENV_VAR`-provided values alike (qfg-2agi.12).** Accepted: `P<n>D`, `T<n>H`, `T<n>M`, `T<n>[.<1-9 digits>]S` in that order, at least one component, ASCII digits, the whole string, up to `P36500D`; milliseconds are exact and rounded half up (`PT0.0005S` = 1 ms, `PT0.999999999S` = 1000 ms). Before, stored values used a lenient parser that accepted `P`, `PT`, `P1DT`, `PT0.5H`, `PT1.5M`, `P0.5D`, `-PT5S`, `P1Y`/`P1M` (as 365/30 days), surrounding whitespace and a trailing newline, read `""` and many malformed strings as `0`, and threw an `OverflowException` at load time on a huge value (dropping that config); `ENV_VAR` values used `XmlConvert` and disagreed with stored values. A malformed duration now follows the malformed-value contract: `GetDuration(key, defaultValue)` returns the default with `Reason.Error` and logs one `Warning` per key (never the raw value); with no `defaultValue`, `GetDuration` under `OnNoDefault.Throw` raises `QuonfigCoercionException`, `GetDurationDetails` reports `Reason.Error`, and `Warn`/`Ignore` return `null`. The same contract now applies to any stored value that a typed getter cannot convert (before: `null` or the default with no log).
- **Changed: under the default `OnNoDefault.Throw`, a plain typed getter called with no `defaultValue` now throws when the config's value cannot be resolved, where it used to return `null` (qfg-2agi.17, qfg-2agi.12).** It throws in exactly these cases: an unset `ENV_VAR` (`QuonfigEnvVarNotSetException`), an `ENV_VAR` that cannot be converted to the config's type (`QuonfigCoercionException`), a decryption failure (`QuonfigDecryptionException`), and a stored value of the right type that the getter cannot convert, for example `GetInt` on a stored integer above `int.MaxValue` (`QuonfigCoercionException`). Before, each of these returned `null` with no log. A missing key still throws `QuonfigKeyNotFoundException` as before. **A config whose value type does not match the getter (for example `GetInt` on a string config) still returns `null` without throwing or logging**, as before; `Get*Details` reports it as `ErrorCode.TypeMismatch`. The plain typed getters are `GetString`, `GetInt`, `GetLong`, `GetBool`, `GetDouble`, `GetStringList`, `GetJson` and `GetDuration`, on the client and on `WithContext`. To keep returning `null`, pass a `defaultValue` or set `OnNoDefault.Warn` / `Ignore`. **The `Get*Details` getters never throw**, under any `OnNoDefault` policy: a missing key or a value that cannot be resolved returns details with `Reason.Error`, an `ErrorCode` (`FlagNotFound`, `TypeMismatch` for a stored value that cannot be converted, `General` for `ENV_VAR` and decryption failures) and the default (or `null`). In every mode the client logs one `Warning` per config key for each of the throwing cases above except a missing key; the warning never contains the raw value. `IsFeatureEnabled` is unchanged.
- **Changed: `Get*Details` no longer throws `QuonfigKeyNotFoundException` for a missing key under `OnNoDefault.Throw` (qfg-2agi.12).** It returns details with `Reason.Error`, `ErrorCode.FlagNotFound` and the default (or `null`), as it already did under `Warn` / `Ignore`. The plain typed getters still throw for a missing key. This keeps the OpenFeature provider, which calls `GetStringListDetails` / `GetJsonDetails` with no default, on the error-reason path.
- **Tests: a client-level test now proves a confidential value evaluated through the public client reaches the evaluation-summary telemetry only in its redacted `*****<md5>` form (qfg-2agi.16).** No behavior change.
- **Tests: the context-merge rule is now pinned (qfg-2agi.38).** New tests with disjoint attributes prove that a named context from a higher tier replaces the whole same-named context and that named contexts it does not mention are kept, for `GlobalContext` + per-call, `GlobalContext` + `WithContext`, nested `WithContext`, and the dev-only `quonfig-user` context under a customer `GlobalContext`. The XML docs on `QuonfigOptions.GlobalContext` and `BoundQuonfig` now say "per named context" instead of the ambiguous "key-by-key". No behavior change.
- **Tests: integration-test-data DURATION cases are now asserted through the public `GetDuration` and `GetDurationDetails` with integer-exact milliseconds (qfg-2agi.4).** The test-only ISO-8601 parser and the +/-1ms tolerance are removed from the harness. No behavior change.

A null value counts as missing. `EvaluationDetails.Metadata` reports `hashPropertyMissing: true` and the client logs one `Warning` per flag. New public members: `EvaluationMatch.MissingHashPropertyName`, an `EvaluationMatch.Matched` overload, and a `Resolver.Resolve` overload that report the missing property.

The client picks up that server's config at the next config change. A client that has never received a real generation still installs every payload.

## 1.3.0 - 2026-09-25

- **Fixed: the SDK now reports its real version in `X-Quonfig-SDK-Version`; previously `dotnet/0.0.1` (qfg-pkig).** `SdkInfo.Version` was a hand-synced literal that stayed at `0.0.1` while the package shipped 1.0.0 -> 1.2.2, so api-delivery and api-telemetry saw every .NET client as `dotnet/0.0.1`. It is now read from the assembly's informational version (fed by `Directory.Build.props`, `+buildmetadata` stripped), so it cannot drift. `SdkInfo.Version` changes from a `const` to a `static readonly` field (same name and type; code that used it in a constant expression, such as an attribute argument, must read it at runtime instead).
- **`ContextUploadMode` now defaults to `PeriodicExample` (was `ShapesOnly`) — more context data is sent to Quonfig by default (qfg-y8je.10).** With `ShapesOnly` the SDK uploaded only context field names and types. With `PeriodicExample` it additionally uploads **example contexts**: for each distinct context `key` (or `trackingId`), at most once per hour, the full evaluation context of that evaluation — every named context (`user`, `team`, ...) including the `GlobalContext`, with **all property values** (for example `user.email`, `user.name`, `team.plan`). Contexts with neither a `key` nor a `trackingId` are never sampled. This matches every other Quonfig SDK (decided 2026-09-25) and powers the dashboard's example-context drill-down. **To keep the old behavior set `ContextUploadMode = ContextUploadMode.ShapesOnly`** (field names and types only, no values), or `ContextUploadMode.None` to send no context data at all; setting `CollectEvaluationSummaries = false` as well turns telemetry off entirely.
- **Telemetry transport policy (qfg-y8je.10).** Telemetry POSTs now have a 15s overall deadline (was 30s, `TelemetryTimeout`) and, on net8.0 when the SDK builds its own HTTP handler, a 5s connect/TLS deadline (`TelemetryConnectTimeout`; an injected `HttpMessageHandler` is never modified). A failed batch (timeout, network error, 408, 429, 5xx) is kept byte-for-byte and resent unchanged, never merged with newer data, so the server dedups a resend of a batch that did land; before, it was dropped. Resends happen no sooner than 30s after a failure and honor `Retry-After` up to 10 min. The retained queue is capped at 5 batches / 2MB / 5 min (oldest dropped; a batch larger than the byte cap is never kept). At most one POST is in flight; the flush interval is a fixed 60s (the adaptive backoff is gone). 401/403/404 disable telemetry for the process with one error; any other 4xx drops that batch with one error. **Logging** goes through `QuonfigOptions.Logger`: a failed POST logs at `Debug`, one `Warning` when data is actually dropped (then a summary at most every 10 min), one `Information` on recovery. Before this, a failure logged a `Warning` every time.
- **A timed-out telemetry POST no longer stops telemetry for the life of the process (qfg-y8je.1).** The sender's `HttpClient.Timeout` (30s) surfaced as a `TaskCanceledException`, which the reporter treated as a shutdown: the flush loop exited and no further telemetry was ever sent, so a single slow api-telemetry response (e.g. a backend stall) silently ended all telemetry. A per-request timeout is now an ordinary failed POST (the batch is kept and resent, see above) and the loop keeps ticking. Contract test T1 pins it.
- **`CloseAsync()` / `DisposeAsync()`** sends the live window once with a 5s deadline and no longer waits on kept batches; it never blocks shutdown on a slow telemetry endpoint. The built-in telemetry `HttpClient` is now disposed on close.
- **Memory caps:** evaluation-summary keys, context-shape fields (before: only context names were capped, so fields grew with traffic) and example contexts are capped at 10,000 per window, and the example-context rate-limit map at 100,000. Keys already recorded keep counting at the cap.
- **New options** on `QuonfigOptions`: `TelemetryTimeout` (15s), `TelemetryConnectTimeout` (5s), `TelemetryMaxRetainedBatches` (5), `TelemetryMaxRetainedBytes` (2,097,152), `TelemetryMaxRetainedAge` (5 min), `TelemetryMaxEvaluationSummaries`, `TelemetryMaxContextShapeFields`, `TelemetryMaxExampleContexts` (10,000 each). Non-positive values fall back to the default. `TelemetryInitialDelay` and `TelemetryMaxInterval` are kept for source compatibility but no longer used: the first POST happens one `TelemetryFlushInterval` after start.
- **Public telemetry types:** `HttpTelemetrySender.DefaultTimeout` is now 15s. `TelemetryReporter.FlushAsync` sends the live window now and no longer throws on a failed POST; `CurrentInterval` is the fixed flush interval; `FlushAndApplyBackoffAsync` is deprecated (runs `FlushAsync`, returns `false` while POSTs are failing); the constructor's `initialDelay` / `maxInterval` are ignored. A custom `ITelemetrySender` that throws is treated as a retryable failure. No wire change, no removed public API, no new dependencies.

## 1.2.2 - 2026-09-14

- **Only a strictly older payload counts as `guardRejected` (qfg-e206, qfg-rr5b).** The reject-older install guard drops any envelope that does not strictly advance the held generation, and every drop was reported as a `guardRejected` failover counter. Two ordinary server behaviors re-deliver an envelope the client already holds at the **same** generation — api-delivery's SSE `sendInitialConfig` re-sends the current envelope on every connect (SDK clients send no `Last-Event-Id`), and a config poll with an empty per-leg ETag slot (a fresh transport, a reconnect, the fallback poller's engage-time fetch) answers with a full 200 — so a perfectly healthy client accumulated one `guardRejected` per SSE reconnect and per cold-ETag poll. `guardRejected` feeds the `sdk_failover` alerting signal, where it is supposed to mean "a leg tried to move us backwards". It now counts **only** a strictly older payload (incoming generation **<** held). An equal-generation re-delivery is a silent no-op: it is still not installed, and it still advances (or, on the SSE push path, still does not advance) `LastSuccessfulRefresh` exactly where it did before — only the counter branch changed. The unversioned carve-out (incoming generation `<= 0` installs rather than being rejected) is untouched. **Operational note: `guardRejected` reads LOWER on 1.2.2 than on 1.2.1 for identical traffic** — the drop is the removal of same-generation re-delivery noise, not a behavior regression; a steady-state client should now report 0. No wire-format, ClickHouse, or dashboard-query change, no public API change, and no new dependencies.

## 1.2.1 - 2026-08-19

- **Fallback poller no longer loses an SSE state edge (qfg-vov2).** The Layer 2 fallback poller decided each tick's wait duration while holding its lock, then released the lock, ran that tick's side effects (engage/disengage callbacks and the fetch), and only then sampled `_sseConnected` a **second** time to establish the baseline it watches for a connection-state change. Any `SetSseConnected()` delivered in that gap was already folded into the baseline, so it never registered as an edge and the worker slept the **full** duration it had decided on: **one hour** on the connected branch, one poll interval on the engaged one. In the severe direction an SSE disconnect that landed in the gap left Layer 2 idle for up to an hour — precisely the outage Layer 2 exists to cover — with the client serving stale config and no fallback polling; in the symmetric direction a reconnect that landed in the gap kept the poller fetching over a healthy stream for a full interval before disengaging. The wait now takes the state the decision was made against as an explicit baseline (and checks it once before the first sleep), so a change in the gap is seen immediately. This matches sdk-go, whose `fallback_poller.go` latches state edges on a buffered channel and cannot lose them. Behavior-only fix; no API change, no new dependencies.

## 1.2.0 - 2026-07-08

- **`QUONFIG_BACKEND_SDK_KEY` / `QUONFIG_ENVIRONMENT` env-var fallbacks (qfg-2qcq.1).** `QuonfigOptions.SdkKey` now falls back to the `QUONFIG_BACKEND_SDK_KEY` env var and `QuonfigOptions.Environment` falls back to `QUONFIG_ENVIRONMENT` when the matching option is left unset, so a service that exports the canonical vars (as `qfg run` and the `fly.*.toml` configs do) can construct with a bare `new Quonfig.Sdk.Quonfig(new QuonfigOptions())`. Precedence is **explicit option > env var** in both cases, matching sdk-go, sdk-node, sdk-python, and sdk-java. In HTTP+SSE (delivery) mode an env-provided `QUONFIG_BACKEND_SDK_KEY` satisfies the SDK-key requirement; in datadir mode an env-provided `QUONFIG_ENVIRONMENT` satisfies the environment requirement. A `QUONFIG_ENVIRONMENT` pin still no-ops (with the existing WARN) in delivery mode, where the SDK key determines the active environment. The `QuonfigOptions.EnvLookup` override still governs the lookup for tests/DI. Additive and backward-compatible; no new dependencies.

- **Runtime telemetry is now actually emitted (qfg-gxm6).** The live client never constructed its `TelemetryReporter`, so sdk-net emitted **zero** runtime telemetry of any kind — evaluation summaries, context shapes/examples, and the qfg-41nh.18 failover counters were all dead despite the collectors and wire format being correct and unit-tested. The client now constructs the reporter (and feeds the evaluation-summary + context collectors from the real evaluation call sites) whenever telemetry is enabled and a sender resolves — delivery mode with an SDK key, or an injected sender. It starts a periodic flush loop and flushes once more on `CloseAsync`/dispose, mirroring sdk-java's reporter lifecycle. Confidential / encrypted values are redacted to the cross-SDK `*****<md5-prefix>` reportable marker before any summary reaches the wire (never plaintext). The existing opt-out is honored: `CollectEvaluationSummaries = false` **and** `ContextUploadMode = None` constructs no reporter and emits nothing. New additive options mirror sdk-java for DI/testing and tuning: `TelemetrySender`, `TelemetryInitialDelay` (8s), `TelemetryFlushInterval` (60s), `TelemetryMaxInterval` (600s). No new dependencies.

- **`QUONFIG_DOMAIN` support + SSE stream follows `ApiUrls` (qfg-41nh.27).** The SDK now derives `ApiUrls` and `TelemetryUrl` from the `QUONFIG_DOMAIN` env var (default `quonfig.com`): `primary.<domain>` / `secondary.<domain>` for config fetch and `telemetry.<domain>` for telemetry, matching the other backend SDKs and the CLI. Resolution precedence per field is explicit option > `QUONFIG_DOMAIN` > built-in production default. The SSE `StreamUrls` now **follow** the resolved `ApiUrls` when not set explicitly (each stream host is the api host with `stream.` prepended), so a customer overriding only `ApiUrls` (e.g. to staging) streams from the matching host instead of silently from `stream.primary.quonfig.com`. Explicit `StreamUrls` / `TelemetryUrl` still win. A single explicit `ApiUrls` entry disables automatic failover and logs a warning at construction. All additive and backward-compatible (the built-in defaults are unchanged); no new dependencies.

- **Failover telemetry emission (qfg-41nh.18).** The SDK now records failover-behavior counters and folds them into the periodic telemetry envelope as an additive `failover` event, alongside evaluation summaries and context shapes. The counters are: `hedgeFired` (config-fetch cycles whose parallel hedge fired the secondary leg), `guardRejected` (installs the reject-older ordering guard dropped, on both the HTTP config-fetch and SSE push paths), and `resolvedFromPrimary` / `resolvedFromSecondary` (which upstream leg served each successful HTTP install; SSE installs are not counted). `resolvedFromLkg` is reserved and always `0`. The event carries no user data, is emitted only when at least one counter is non-zero in the flush window (a healthy client emits nothing), and honors the existing telemetry opt-out (`CollectEvaluationSummaries = false` **and** `ContextUploadMode = None` records nothing). The wire field names are camelCase, matching the cross-SDK contract (mirrors sdk-go). No new dependencies.

## 1.1.1 - 2026-07-03

Backward-compatible patch (qfg-41nh.8, part of the coordinated 1.1.1 hardening train).

- **SSE stream pinned to the primary (the f05 invariant).** The reconnect loop previously walked the whole `StreamUrls` list, so an outage on the primary stream endpoint silently repointed the long-lived SSE stream at the secondary — binding real-time config freshness to the mirror, which is sized for poll traffic only. The stream is now pinned to `StreamUrls[0]` and a dead primary is retried forever with the existing exponential backoff; SSE never fails over. During a stream outage the Layer 2 fallback poller (whose hedged HTTP fetch keeps BOTH `ApiUrls` legs) covers freshness. The failover chaos suite's f05 probe, previously hardcoded off, is now wired to the client's real stream-leg bookkeeping, so a regression that reintroduces stream-leg walking fails CI.
- **Honest freshness stamping.** `LastSuccessfulRefresh` no longer advances when an SSE-pushed envelope is REJECTED by the reject-older guard — a stale replay loop previously reported an effectively frozen client as fresh. Conversely, an HTTP poll the server ANSWERS with nothing newer to install (a 304, or a same/older-generation payload the guard discards) now DOES advance the stamp: a successful poll is a successful refresh (sdk-go semantics).
- **Operator logging.** With any wired `ILogger` the client now emits: one startup line announcing the chosen polling mode (`quonfig: polling configuration mode=...`, Information), a Warning when the Layer 2 fallback poller ENGAGES (SSE down past threshold — the outage signal to alert on), and an Information line when it DISENGAGES (SSE recovered). The default logger remains the no-op `NullLogger`.

## 1.1.0 - 2026-07-01

Backward-compatible minor. Hardens the HTTP config-fetch path for fast, regression-free failover.

- **Parallel-failover hedge on the HTTP config-fetch (qfg-7h5d.1.14).** The init/refresh config fetch is now a parallel hedge: the SDK fires the **primary** URL first and, only if it answers within the hedge delay (~2s), the primary wins and the **secondary is never contacted** (cold standby, zero extra load on a healthy system). If the primary is slow past the hedge delay or errors fast, the SDK *also* fires the secondary **in parallel** (without cancelling the primary). Each arriving leg is installed through the existing reject-older guard, so watermark-max falls out: the higher `Meta.generation` wins, a late older payload never regresses an established client, and a late newer payload heals forward. SSE is untouched by the hedge. (Correction: this entry originally claimed SSE "never fails over" — at 1.1.0 the stream still walked the `StreamUrls` list on reconnect; the primary pin shipped in the next patch, see Unreleased.)
  - Two new additive options: `QuonfigOptions.ConfigFetchHedgeDelay` (default ~2s — how long to wait for the primary before hedging the secondary) and `QuonfigOptions.ConfigFetchHedgeAbort` (default ~6s — the per-leg hard-abort deadline). The existing `ConfigFetchTimeout` is unchanged and still governs the sequential `FetchAsync` path. A warning is logged at construction if `InitTimeout <= ConfigFetchHedgeAbort`.
  - **Backward-compatible behavioral notes.** `resolvedFrom` may now return `"primary"` in a fast-both topology where 1.0.0 (sequential) returned `"secondary"` only on a primary failure; an extra post-ready config-update callback may fire when a late-but-newer leg heals forward; and ETags are now tracked **per leg** (each URL has its own slot) so a 304 from one leg can no longer mask the other and there is no cross-leg ETag data race.

- **Failover + canonical-ordering reliability (qfg-7h5d.1.11).** Two additive, backward-compatible hardening changes proven red→green against the shared failover + ordering chaos corpus:
  - **Per-URL config-fetch timeout.** Each failover leg now gets its own deadline so a hung or slow primary aborts fast (~3s default) and the secondary is reached within the overall `InitTimeout`, instead of the primary starving the whole budget. Tunable via the new `QuonfigOptions.ConfigFetchTimeout` option (default 3s); applies to the initial fetch, the fallback poller, and in-band refresh.
  - **Reject-older install guard.** The SDK now reads the monotonic `Meta.generation` watermark and installs a network envelope only if it advances the held generation, with one carve-out for unversioned snapshots (below). A fresh client always accepts its first snapshot; an established client never regresses to an older versioned payload (e.g. on a failover to a stale secondary), and a same-generation snapshot is a no-op. Applies to every network install path (initial fetch, fallback poller, SSE snapshot/update, refresh). Datadir/datafile installs are a local source of truth and bypass the guard.
    - **Install-guard carve-out for unversioned snapshots.** A delivery payload whose `generation` is absent or `<= 0` (e.g. from a server that predates the generation watermark) is installed by an established client rather than rejected as older. Defensive back-compat guard — with servers that emit true generations it never triggers.
